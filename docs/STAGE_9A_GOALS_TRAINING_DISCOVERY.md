# Stage 9A — Goals ↔ Training ↔ Progress Discovery\n\n## Scope\nDefine the contract that connects existing Goals, completed Training execution, Progress metrics, and the adaptive training loop without hidden plan mutations.\n\n## Current foundations\n- Goals are user-owned, have lifecycle/status, priority, optional metric/baseline/target and metadata.\n- Goal progress already derives from completed owned TrainingSessionDB + TrainingSetResultDB data.\n- Training evaluation derives deterministic per-exercise decisions from completed session snapshots.\n- Adaptation derives bounded next-exercise values from evaluation.\n- Adaptive revisions are versioned, audited, user-scoped and concurrency-safe.\n- Progress endpoints already expose exercise history/trends/records.\n\n## Current gap\nThe systems are connected only indirectly: Goal → Progress reads training data, while Training → Adaptation does not know which active goals should be served by the next plan.\n\nThere is currently no canonical domain contract answering:\n1. Which active goals are relevant to a training plan?\n2. Which goal metrics/evidence should influence training priorities?\n3. How should multiple goals be prioritized without allowing one goal to silently override safety or deterministic adaptation?\n4. How should goal progress explain whether the current training loop is serving the goal?\n\n## Stage 9 design principles\n1. Goals remain intent, not direct commands. A goal may influence priority/focus, but must not directly mutate exercise load.\n2. Training safety wins. Recovery constraints, insufficient data, high effort and bounded adaptation remain authoritative.\n3. Deterministic. The same user state and completed evidence must produce the same goal-training signals.\n4. User-scoped. No goal or progress data may cross users.\n5. Explainable. Every training-facing goal signal carries goal id, metric, current value, target, priority and reason.\n6. No hidden persistence in read paths. Discovery/preview endpoints remain read-only.\n7. Separate signal from actuation. Stage 9 first creates a canonical goal-training signal layer; later stages may consume it for planning/Decision Engine.\n\n## Proposed Stage 9 sequence\n- 9A Discovery — this contract and gap analysis.\n- 9B Goal Training Signals — pure deterministic service mapping active goals to training-relevant signals.\n- 9C Goal-aware planning input — expose signals to planner/effective-plan context without changing loads automatically.\n- 9D Goal ↔ Progress feedback — explain goal contribution, trajectory and evidence.\n- 9E Goal-aware adaptation guardrails — only bounded, evidence-backed priority/focus adjustments; never bypass Stage 8 safety.\n- 9F Full regression/security gate.\n\n## Initial signal contract\nFor each eligible active metric goal:\n- goal_id\n- title\n- goal_type\n- priority\n- metric_key\n- direction\n- baseline_value\n- current_value\n- target_value\n- progress_pct\n- remaining\n- trend\n- on_track\n- target_date\n- urgency/trajectory classification\n- exercise_key when explicitly configured\n- reason_codes\n\nThe signal is derived from the existing canonical goal-progress calculation and completed training evidence. It does not write to the database.\n\n## Eligibility\nOnly active goals with a supported metric and sufficient evidence participate in training signals. Goals without a metric remain visible in goal management but do not silently affect training.\nExercise-specific metrics are linked only when the goal explicitly declares metadata.exercise_key. No fuzzy exercise-name matching.\n\n## Priority and conflict policy\nPriority determines ordering, not permission to violate safety. If several goals compete:\n- higher priority is surfaced first;\n- explicit exercise-linked goals outrank generic goals for that exercise;\n- safety constraints always override goal preference;\n- no automatic load increase is justified solely by goal urgency.\n\n## Acceptance criteria for 9A\n- Existing Goal and Training contracts are documented.\n- No implementation changes are required to close discovery.\n- Stage 9 implementation starts from a pure signal layer, not from route-level side effects.
